# hw-01 — стенд для показов в Yandex Cloud

Учебный стенд по курсу «Инфраструктура как код», вариант 11. Веб-серверы в двух зонах доступности стоят за сетевым балансировщиком, рядом с ними — сервер приложения без публичного адреса. Стенд поднимается одной командой перед показом и сносится после него, чтобы не платить за простой, и продолжает отвечать клиентам, если одна из веб-машин отказала.

Все ресурсы получают имена с префиксом `derevyanko-11` и метки `env=test`, `owner=derevyanko-11`.

## Схема

Для умолчаний варианта (`WEB_COUNT=2`):

```
                     клиент
                       │ HTTP :80
          ┌────────────▼────────────┐
          │    derevyanko-11-lb     │  сетевой балансировщик
          └─────┬─────────────┬─────┘
                │ :8033       │ :8033
   ┌────────────▼───┐   ┌─────▼──────────┐
   │     web-1      │   │     web-2      │   nginx, публичный IP для SSH
   │ ru-central1-b  │   │ ru-central1-d  │
   └────────┬───────┘   └────────────────┘
            │ внутренний адрес :8033
   ┌────────▼───────┐
   │     app-1      │   без публичного IP,
   │ ru-central1-b  │   в интернет — через NAT-шлюз
   └────────────────┘
```

## Из чего состоит

| Ресурс | Имя | Назначение |
|---|---|---|
| Сеть | `derevyanko-11-net` | общая сеть стенда |
| Подсети | `derevyanko-11-subnet-a` (ru-central1-b, 10.21.1.0/24)<br>`derevyanko-11-subnet-b` (ru-central1-d, 10.21.2.0/24) | по подсети на зону доступности |
| NAT-шлюз | `derevyanko-11-nat` | выход в интернет для машин без публичного адреса |
| Таблица маршрутизации | `derevyanko-11-rt` | маршрут `0.0.0.0/0` через NAT-шлюз, привязана к `subnet-a` |
| Веб-серверы | `derevyanko-11-web-1` … `web-N` | nginx на порту 8033 отдаёт страницу `devlab on <имя машины>`; нечётные номера — в зоне a, чётные — в зоне b |
| Сервер приложения | `derevyanko-11-app-1` | такой же nginx в `subnet-a`, публичного адреса нет |
| Целевая группа | `derevyanko-11-tg` | внутренние адреса веб-серверов |
| Балансировщик | `derevyanko-11-lb` | слушает HTTP на порту 80 и распределяет запросы на порт 8033 веб-серверов; проверяет их по HTTP `/` каждые 2 с и выводит машину из балансировки после двух неудачных проверок подряд |

Все машины одинаковые: платформа standard-v3, 2 vCPU с гарантированной долей 20 %, 2 ГБ RAM, прерываемые, загрузочный диск network-hdd 20 ГБ, Ubuntu 24.04 LTS. Настраиваются через cloud-init: пользователь `student` с SSH-ключом, установка nginx, перевод его на порт `APP_PORT`, страница с приветствием `GREETING`.

## Файлы

```
hw-01/
├── create.sh             поднимает стенд с нуля, повторный запуск безопасен
├── check.sh              проверяет стенд, код возврата 0 или 1
├── destroy.sh            удаляет всё с префиксом стенда
├── cloud-init.tpl.yaml   шаблон настройки машин
└── README.md
```

## Как поднять и снести

```bash
cd hw-01
./create.sh      # поднять стенд
./check.sh       # проверить, что он работает
./destroy.sh     # снести
```

В конце `create.sh` печатает адрес балансировщика: `Балансировщик: http://<IP>/`. nginx устанавливается на машинах уже после того, как скрипт завершился, поэтому первые несколько минут балансировщик может не отвечать и `check.sh` будет возвращать ошибку. Подождите 2–3 минуты и повторите проверку.

Время подъёма и сноса для отчёта:

```bash
time bash create.sh
time bash destroy.sh
```

Стенд тарифицируется всё время, пока он поднят. После показа обязательно запускайте `destroy.sh`.

## Параметры create.sh

| Аргумент | Переменная | По умолчанию | Что задаёт |
|---|---|---|---|
| `--prefix` | `PREFIX` | `derevyanko-11` | префикс имён всех ресурсов и значение метки `owner` |
| `--env` | `ENV_NAME` | `test` | значение метки `env` |
| `--web-count` | `WEB_COUNT` | `2` | число веб-серверов, целое больше нуля |
| `--port` | `APP_PORT` | `8033` | порт nginx на машинах; балансировщик слушает 80 и пересылает сюда |
| `--greeting` | `GREETING` | `devlab` | текст на странице: `<GREETING> on <имя машины>` |
| `--zone-a` | `ZONE_A` | `ru-central1-b` | зона первой подсети |
| `--zone-b` | `ZONE_B` | `ru-central1-d` | зона второй подсети |
| `--cidr-a` | `CIDR_A` | `10.21.1.0/24` | диапазон первой подсети |
| `--cidr-b` | `CIDR_B` | `10.21.2.0/24` | диапазон второй подсети |
| — | `BOOT_SIZE` | `20` | размер загрузочного диска, ГБ |
| — | `IMAGE_FAMILY` | `ubuntu-2404-lts` | семейство образа ОС |
| — | `SSH_KEY_FILE` | `~/.ssh/id_ed25519.pub` | открытый ключ для пользователя `student` |

Примеры:

```bash
./create.sh --web-count 3                  # три веб-сервера
WEB_COUNT=3 ./create.sh                    # то же через переменную
WEB_COUNT=4 ./create.sh --web-count 3      # аргумент важнее: будет три
./create.sh --prefix demo --greeting hello # отдельный стенд с другим префиксом
```

Неизвестный аргумент или аргумент без значения завершает скрипт с ошибкой до того, как в облаке что-либо создано.

### Повторный запуск

`create.sh` можно запускать на уже поднятом стенде сколько угодно раз. Перед созданием каждого ресурса он проверяет, есть ли ресурс с таким именем, и если есть — печатает `... уже есть, пропускаю`. Дубликаты не появляются, скрипт не падает.

Машины прерываемые: облако может остановить их в любой момент и обязательно останавливает через 24 часа работы. Повторный запуск `create.sh` находит остановленные машины и включает их.

Повторный запуск не меняет то, что уже создано:

- `--port` и `--greeting` применяются только к новым машинам — cloud-init отрабатывает один раз при первой загрузке, а слушатель балансировщика не пересоздаётся;
- увеличение `--web-count` создаёт недостающие машины, но уже существующая целевая группа не обновляется, и новые машины в балансировку не попадают;
- уменьшение `--web-count` лишние машины не удаляет.

Чтобы поменять эти параметры, снесите стенд и поднимите его заново.

## Параметры check.sh и destroy.sh

Эти скрипты аргументов не принимают, только переменные окружения:

| Скрипт | Переменные |
|---|---|
| `check.sh` | `PREFIX`, `APP_PORT`, `GREETING` |
| `destroy.sh` | `PREFIX` |

Если стенд поднимался не с умолчаниями, передайте те же значения:

```bash
./create.sh --prefix demo --port 8080 --greeting hello
PREFIX=demo APP_PORT=8080 GREETING=hello ./check.sh
PREFIX=demo ./destroy.sh
```

## Проверка стенда: check.sh

Скрипт печатает по строке на каждую проверку:

1. балансировщик отвечает кодом 200;
2. ответы приходят больше чем с одной машины — скрипт делает 12 запросов к балансировщику и собирает имена машин из страниц;
3. сервер приложения доступен с `web-1` по внутреннему адресу — скрипт заходит на `web-1` по SSH и оттуда запрашивает страницу `app-1`;
4. дополнительно: сервер приложения не отвечает снаружи.

Код возврата `0`, если прошли все проверки, `1` — если не прошла хотя бы одна.

Исправный стенд:

```
✓ балансировщик отвечает: 200
✓ ответили машины: derevyanko-11-web-1 derevyanko-11-web-2
✓ сервер приложения отвечает с derevyanko-11-web-1: devlab on derevyanko-11-app-1
✓ сервер приложения снаружи недоступен
```

Со стендом из одной веб-машины (`--web-count 1`) вторая проверка не проходит никогда: распределять нагрузку не на что.

### Проверка отказа машины

Остановите nginx на одной из веб-машин и запустите проверку ещё раз:

```bash
WEB2_IP=$(yc compute instance get derevyanko-11-web-2 --format json \
  | jq -r '.network_interfaces[0].primary_v4_address.one_to_one_nat.address')

ssh student@"$WEB2_IP" 'sudo systemctl stop nginx'
sleep 10        # балансировщику нужно около 4 с, чтобы вывести машину
./check.sh; echo "код возврата: $?"

ssh student@"$WEB2_IP" 'sudo systemctl start nginx'
```

Ожидаемый результат:

```
✓ балансировщик отвечает: 200
✗ ответила одна машина: derevyanko-11-web-1
✓ сервер приложения отвечает с derevyanko-11-web-1: devlab on derevyanko-11-app-1
✓ сервер приложения снаружи недоступен
код возврата: 1
```

Так и должно быть: для клиента сервис жив, балансировщик по-прежнему отвечает 200, но распределения больше нет, стенд не в норме, поэтому код возврата 1.

## Если check.sh вернул ошибку

Сначала убедитесь, что `PREFIX`, `APP_PORT` и `GREETING` совпадают с теми, с которыми запускался `create.sh`, и что после создания прошло хотя бы 2–3 минуты. Дальше — по строке, которая не прошла.

**✗ балансировщик derevyanko-11-lb не найден.** Стенд не поднят или указан не тот `PREFIX`. Запустите `./create.sh`.

**✗ балансировщик отвечает: 000 (или другой код).** Балансировщик не нашёл ни одной здоровой машины.

- Проверьте, что машины запущены: `yc compute instance list`. Если есть `STOPPED`, запустите `./create.sh` ещё раз — он включит остановленные машины.
- Посмотрите, какие машины балансировщик считает здоровыми, и зайдите на нездоровую: работает ли nginx, чем закончился cloud-init (команды ниже).

**✗ ответила одна машина.** Здоровой балансировщик считает только одну машину: на остальных остановлен nginx или остановлена сама машина. Запустите nginx (`sudo systemctl start nginx`) или машину (`./create.sh`). Если в строке написано `нет ответов`, а первая проверка при этом прошла, — `GREETING` для `check.sh` не совпадает с тем, что передавался `create.sh`.

**✗ сервер приложения недоступен с derevyanko-11-web-1.** Проверка состоит из двух шагов, и сломаться может любой.

- SSH до `web-1`. `check.sh` заходит как `student` ключом по умолчанию и без запроса пароля. Проверьте вручную: `ssh student@<внешний IP web-1> hostname`. Если ssh отказывает — закрытый ключ не соответствует открытому из `SSH_KEY_FILE`, с которым поднимался стенд; добавьте нужный ключ (`ssh-add <путь к ключу>`).
- Запрос с `web-1` к `app-1`. У `app-1` нет публичного адреса, и nginx он устанавливает через NAT-шлюз. Проверьте, что таблица маршрутизации привязана к подсети: `yc vpc subnet get derevyanko-11-subnet-a --format json | jq .route_table_id` не должно выводить `null`. Затем зайдите на `app-1` через `web-1` и посмотрите лог cloud-init. Если настройка не прошла, удалите машину (`yc compute instance delete derevyanko-11-app-1`) и запустите `./create.sh` — он создаст заново только её.

**✗ сервер приложения виден снаружи.** У `app-1` появился публичный адрес: проверьте поле `one_to_one_nat` в `yc compute instance get derevyanko-11-app-1`. Удалите машину и запустите `./create.sh`, он пересоздаст её без публичного адреса.

## Снос стенда: destroy.sh

`destroy.sh` не полагается на то, что в облаке ровно то, что создавал `create.sh`: он ищет ресурсы, чьё имя начинается с `PREFIX`, и удаляет всё найденное в порядке зависимостей:

балансировщики → целевые группы → машины → диски → зарезервированные адреса → отвязка таблиц маршрутизации от подсетей → таблицы маршрутизации → NAT-шлюзы → подсети → сети.

В конце скрипт печатает, сколько ресурсов с префиксом осталось; после успешной уборки везде 0. Повторный запуск на пустом каталоге ничего не удаляет и тоже не падает.

Диски и зарезервированные адреса тарифицируются, даже когда машин уже нет, поэтому после уборки стоит проверить их отдельно:

```bash
yc compute disk list
yc vpc address list
```
